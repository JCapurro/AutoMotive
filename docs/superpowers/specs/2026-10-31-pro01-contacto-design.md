## Decisiones de diseño

### Filtro estricto

1. **Forma.** `filters.seller_types: ["private"] | ["dealer"]`. Se guarda como array por compatibilidad con el backlog, pero la UI elige uno solo (ambos = sin filtro, no se guarda). No se guarda `dealer_inferred`: `["dealer"]` lo incluye vía `effective_seller`. Una tercera opción que nadie elige solo agrega estado.
2. **Hard check `seller`** (clave distinta de la blanda `seller_type`, para no chocar en `match_reasons`). `None` → `UNKNOWN`; `effective_seller ∈ seller_types` → `OK`; si no → `FAIL`. Solo corre si `profile["seller_filter"]` es true; si no, devuelve `None` (filtro ausente).
3. **Gating en lectura, siempre, sin costo en el camino caliente.** `_SELECT` (crawl por `alerts_for_target`, rematch, rescore, `model_less_alerts`, listado) y la SQL de `low_results` suman
   ```sql
   CASE WHEN sp.filters ? 'seller_types'
        THEN public.plan_feature(sp.user_id, 'seller_filter') ELSE false END AS seller_filter
   ```
   y `_to_alert` lo pasa al dict del perfil. `plan_feature` llama a `plan_limits_for`, que cuenta las `search_profiles` del usuario en cada llamada: por fila sería el patrón del corte del 2026-10-30 (`profiles.py:35-41`). El `CASE` solo la evalúa para las búsquedas que tienen la clave (hoy ninguna; mañana, las estrictas de Pro y las de quien bajó de plan), así que el resto de las filas no paga nada. Si la medición de la Task 3 muestra regresión igual (muchos Pro estrictos), el plan B es un CTE `MATERIALIZED` por `user_id` distinto, como `LIVE_SEARCHES`. Cubre el bypass por PostgREST y el downgrade con filtro guardado. Semántica de `threshold_alerts`: Pro-only también durante el piloto (no mira `enforced`). **No** se agrega rechazo por plan en `enforce_plan_features`.
4. **Sin doble conteo y sin perder la preferencia blanda.** En `_preferences`:
   - hard activo (`seller_filter` true y `seller_types` presente): se omite la blanda `seller_type`;
   - `seller_filter` false y `seller_types` presente (bajó de plan, o lo escribió por API sin ser Pro): `seller_types[0]` se usa como la blanda `seller_type`. Así Particular conserva la preferencia blanda, como decidió Juan;
   - sin `seller_types` (todas las búsquedas de hoy): exactamente igual que hoy.
   Solo cambian los perfiles con la clave nueva, que hoy no existen: **sin bump, sin rescore masivo.** `preview_search` y `low_results` ignoran `seller_types` sin el flag (la blanda no filtra).
5. **Validación de forma en la base.** `search_filters_problem` (`create or replace` desde `20261030120000:165-176`; sigue `immutable` y conserva los grants) suma: `seller_types` ausente, JSON `null`, o array de 1 elemento en `('private','dealer')`. Rechaza basura escrita por API.
6. **Formulario (Pro).** El campo «Vendedor» sigue siendo el mismo select (label y opciones intactas para Particular: no rompe `seller.spec.ts`). Para Pro las opciones se rotulan «Particulares» y «Agencias (incluye posibles agencias)», y debajo hay un checkbox «Solo este tipo de vendedor». Con el check: se guarda `filters.seller_types = [valor]` y no `preferences.seller_type`; la pista cambia a «Descartamos los otros. Si la publicación no dice quién vende, el aviso pasa con menos puntaje.» (sin repetir «Incluye posibles agencias.»: ya lo dice la opción). En el resumen de la búsqueda, fila «Vendedor: Solo particulares» / «Solo agencias (incluye posibles agencias)». Envuelve en 375 px (texto en bloque, sin Segmented).
7. **Formulario (no Pro).** Sin control nuevo ni upsell (patrón del umbral, `search-form.tsx:936-943`). Si la búsqueda ya tiene `seller_types` (bajó de plan): `fromProfile` lee `prefs.seller_type ?? f.seller_types?.[0] ?? ""` (hoy solo lee `prefs.seller_type`, `web/lib/search-form.ts:222`), así el select muestra el valor que el worker usa como preferencia blanda (decisión 4). Debajo, el aviso «Filtro estricto: solo Pro. En tu plan se usa como preferencia.» con un botón «Quitar filtro estricto». El resumen muestra «Vendedor: Particulares (preferido; filtro estricto solo Pro)».
8. **Acción del servidor.** `my_plan_feature('seller_filter')` en el `Promise.all` de `save()`. **Solo poner** el filtro requiere Pro; **quitarlo** se puede en cualquier plan:
   - con la feature: `seller_types` se valida con zod (array de 1 elemento en `private|dealer`; otra forma → error, no se guarda);
   - sin la feature: si el input trae `seller_types` vacío o ausente (botón «Quitar», o cambió el select), se guarda sin la clave y el select va a `preferences.seller_type`; si trae el mismo valor que lo guardado, se conserva; cualquier otro valor se ignora y se conserva lo guardado (nunca se pone uno nuevo).
   Así un valor viejo no queda para siempre (cambia la clave del índice único y volvería al recuperar Pro) y la edición sin tocar el vendedor no dispara un rematch espurio. `seller_filter_set {profile_id, seller_types, mode}` en el alta con valor y en la edición cuando cambia (incluye pasar a vacío). El rematch lo dispara `matchingChanged`.

### Mensaje listo

13. **Forma.** Funciones puras gemelas (`worker/intelligence/contact_message.py`, `web/lib/contact-message.ts`) con JSON dorados compartidos en `worker/tests/fixtures/contact_message/` (`golden.json` para el render, `lint.json` para la regla), que leen pytest y vitest, como PAR-01. Entrada: plantilla (o null), `catalog_model` y `year`, y preguntas específicas. **Nunca el `title`** ni otro texto scrapeado.
14. **Plantilla.** Marcadores `{auto}` y `{preguntas}`; uno por línea. Por defecto:
    ```
    Hola, vi tu {auto} publicado.
    {preguntas}
    ¿Cuándo se puede ver?
    ```
    `{auto}` = `«{modelo} {año}»` con el modelo de `vehicle_catalog` (el join que ya usa `rows_for_scoring`, `listings.py:305-307`, expuesto como `catalog_model`) y el año solo si es un entero razonable; sin modelo de catálogo, «auto». El valor además tiene que cumplir `^[\p{L}\p{N} .-]{1,40}$`, si no, «auto». `{preguntas}` = «¿Lo seguís teniendo?» + la primera pregunta específica (`question_texts(limit=1)`), o «¿Sos titular?» si no hay ninguna: siempre dos líneas, así el mensaje por defecto queda en 4. Ejemplo: «Hola, vi tu Fiesta 2017 publicado. / ¿Lo seguís teniendo? / ¿Tenés historial de services? / ¿Cuándo se puede ver?». Se reutilizan los textos de `QUESTION` sin reescribirlos; `seller_questions()` y `question_texts()` no cambian.
15. **Render seguro.** Reemplazo literal en una sola pasada de exactamente `{auto}` y `{preguntas}` (regex `\{(auto|preguntas)\}` con función de reemplazo; el texto insertado no se vuelve a escanear). **Nunca `str.format`** ni template literals: con una plantilla escrita por API, `{`, `{x}` o `{auto.__class__}` lanzarían o filtrarían atributos dentro de `on_matches`. Antes de renderizar, la plantilla guardada pasa por la misma regla de lint (decisión 17); si falla, o si el render lanza por cualquier motivo, se usa la plantilla por defecto (`try`/fallback, con `log.warning` en el worker). Un mensaje mal armado nunca tira el lote de notificaciones. Tests con plantillas hostiles en `lint.json`/`golden.json`: `{`, `}{`, `{x}`, `{auto.__class__}`, `{0}`, `{{auto}}`, `%s`, una URL, un teléfono, un término prohibido, 501 caracteres.

    - máx. 500 caracteres y 6 líneas; solo `{auto}` y `{preguntas}` como marcadores, y ninguna otra llave suelta;
